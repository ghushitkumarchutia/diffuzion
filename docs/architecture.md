# Diffuzion foundation decisions

The development blueprint is preserved byte for byte in `Diffuzion_Development_Blueprint.md`. This document records Day 1 implementation decisions; it does not replace that blueprint.

## Boundaries

Next.js owns presentation and Better Auth. FastAPI owns domain rules. The future API and worker share the Python application. Day 1 provided configuration, contracts and helpers. Day 2 adds the mounted Better Auth handler, application models/migrations, verified-account dependencies and the operator Admin CLI. Protected domain routes, analysis execution and payments remain future-stage work.

The root page is a minimal scaffold required to verify the App Router build. Playwright configuration, two foundation smoke tests, backend helper/contract tests and the root Makefile are verification dependencies. Generated scaffold branding, images and optional framework features were removed. `agentRules: false` prevents Next.js from adding an unapproved AGENTS.md file.

## Tested compatibility set

- Node.js 24.21.0 with its bundled npm; Python 3.12.13; uv 0.13.0.
- Next.js 16.4.0, React 19.3.0, TypeScript 5.9.3, Better Auth and its `auth` CLI 1.7.7.
- FastAPI 0.143.0, Pydantic 2.14.1, SQLAlchemy 2.1.4 and mypy 2.4.0.
- Tree-sitter 0.26.0, JavaScript grammar 0.25.0 and TypeScript grammar 0.23.2.
- Full dependency resolutions are generated by npm and uv in their lockfiles. Use `npm ci` and `uv sync --locked`.

Mypy is the selected Python type checker. It runs in strict mode with the Pydantic plugin. The project is a nonpackaged uv application, restricted to Python 3.12. Root commands explicitly set `PYTHONPATH=apps/api` and select the API's type-check configuration.

Starlette is constrained to `>=0.46,<1` to preserve the approved httpx-based TestClient integration. AnyIO is constrained to `>=4,<4.15` to avoid the deprecated BlockingPortal alias warning in that compatible Starlette release. The resolved releases are Starlette 0.52.1 and AnyIO 4.14.2. No warnings are suppressed in project configuration.

## Configurable safety defaults

| Previously unspecified setting       | Day 1 default                               |
| ------------------------------------ | ------------------------------------------- |
| YAML depth                           | 50                                          |
| YAML nodes                           | 20,000                                      |
| YAML aliases                         | 0; reject all aliases                       |
| Parser memory on Linux               | 256 MiB address-space ceiling               |
| Combined parser stdout/stderr        | 4 MiB                                       |
| Parser execution timeout             | 30 seconds                                  |
| IP requests                          | 240 per minute                              |
| Auth requests                        | 20 per minute                               |
| Rate-limit identity windows          | 10,000 maximum                              |
| Trusted proxy peers                  | Explicit loopback IPs for local development |
| Browser mutation marker              | `X-Diffuzion-Request: 1`                    |
| Generated frontend contract location | `apps/web/lib/api-types.d.ts`               |

These are conservative implementation defaults, not measured production thresholds. Parser helpers accept only explicit absolute trusted executables, remove inherited secrets from child environments, cap combined output, and kill/reap the process group on failure. Linux applies the memory limit in an isolated launcher before executing the trusted program. macOS checks verify timeout, output and cleanup; the Linux address-space ceiling has not been exercised on a Linux host because Docker is unavailable here.

The same-origin helper exempts only POST to the exact Razorpay webhook path. That exemption does not verify a webhook: its future handler must verify the raw-body HMAC. Forwarded client IPs are accepted only from explicitly configured proxy peers; deployment must configure the actual private proxy IP and append or overwrite forwarding headers correctly.

Rate windows are process-local, locked, bounded and expiring. A full identity table rejects new identities with a retryable 429 rather than evicting active limits. These soft limits do not replace future database quota and AI-budget admission checks.

Environment values are injected explicitly. Python settings never load a dotenv file implicitly. Frontend configuration is marked server-only, validates the auth schema connection and exposes a separate allowlisted public-origin object. Neither module validates configuration at import time. Server credentials fail clearly when runtime getters are called without valid values. Node-run tooling uses explicit relative `.ts` imports and the React server condition when importing the server-only environment module.

## Verification boundaries

Foundation tests exercise helpers and DTOs against a temporary FastAPI test app. They do not establish live OAuth, payment, database-locking or provider integration. The UI build and browser tests exercise the minimal homepage, keyboard navigation and safe missing-page response. A temporary browser harness additionally verifies dialog focus restoration, Escape behavior, pending confirmation protection and escaped feedback text. Dependency smoke checks parse representative TS/JS calls and validate a small self-contained OpenAPI 3.0 document; they do not implement call extraction or oasdiff.

The final local `make check` completed successfully: 64 backend tests, 2 Chromium browser tests, ESLint, Ruff lint/format checks, strict TypeScript, strict mypy and the Next.js standalone production build. Locked npm and uv reinstalls succeeded. A temporary FastAPI schema containing the DTOs was accepted by openapi-typescript; its generated smoke output was removed from the workspace. No staging or commits were performed.

## Day 2 decisions and boundaries

The approved generated auth history location is `apps/web/auth-migrations/versions/`. SQL comes from the pinned Better Auth CLI, is retained for review and is compared with pending CLI output before application. The initial application revision identifier is explicitly `0001_initial_app`, with the required `initial_app_schema.py` filename. Its scaffold came from Alembic; the resulting migration was reviewed and edited for the approved invariants. Alembic filters out auth-owned objects and the extension and keeps its version table in `app`.

The reference-only `auth.user` metadata contains the verified text primary key. It is not an application ORM model. Model files depend on Base and string FK targets, and the package registers all four groups. A single unique `quota_periods.purchase_id` represents the purchase/pass relationship; a redundant reverse purchase FK is omitted, so there is no purchase/period import or table cycle.

The initial upload reservation window is a configurable 600 seconds (`UPLOAD_RESERVATION_SECONDS`). File rows represent in-flight storage reservations with `upload_reserved_bytes`, `upload_started_at` and `upload_expires_at`. Uploading rows must contain positive reserved bytes and both ordered timestamps; stored/deleting rows carry no active reservation. Stored rows require their source hash and storage key. Later upload/maintenance services will reserve under the account lock, refresh/reconcile expiry and clear these fields together with the aggregate account counter. No new reservation table is needed. Original source and frozen revision/run snapshot immutability remain service responsibilities when those services are implemented.

Sessions last seven days without refresh or cookie caching. Secure, HttpOnly, SameSite=Lax cookies are used in production; origin and CSRF checks are explicitly enabled, including in test configurations. GitHub OAuth initiation requests no repository scope. The browser callback helper and server reject external destinations. Better Auth handles OAuth state/PKCE; there are no custom OAuth endpoints.

FastAPI forwards only the appropriate allowlisted session cookie to the fixed internal session endpoint, disables redirects/environment proxy discovery, bounds timeout/response handling and validates session/user IDs and expiry. It verifies before starting account SQL, creates accounts idempotently, reloads current status/role and ends the transaction before returning. Database session contexts roll back on exceptions and close reliably; callers commit within short explicit transactions.

The test-only helper requires an isolated database/role named `diffuzion_test`, loopback origin, dedicated synthetic credentials, the initial app migration and explicit test opt-in. It uses a separate unmounted testUtils auth instance and genuine signed sessions. Production options contain neither testUtils nor the Admin plugin. Operator Admin assignment requires an existing active verified-login account and records a bounded audit reason.

Local PostgreSQL validation uses the user-approved native temporary instance, with `listen_addresses=''` and a private Unix socket. pgvector 0.8.2 was built from the official pinned tag and installed as a PostgreSQL 17 prerequisite; existing databases were not modified. Docker is still required for subsequent deployment work. Complete real Google/GitHub OAuth authorization is not claimed without registered credentials and manual callback validation.

Day 2's complete local `make check` passed: 83 backend tests, 9 Chromium/browser API tests, ESLint, Ruff lint/format checks, strict TypeScript, strict mypy and the standalone Next.js build. The native test runtime was PostgreSQL 17.5 (Homebrew) with pgvector 0.8.2. Additional checks verified the operator CLI's idempotent Admin assignment, repeatable bootstrap/auth verification and offline Alembic SQL generation. These counts include the retained Day 1 regression tests. No files were staged and no commits were executed by the assistant.
